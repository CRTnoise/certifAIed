01
Phase A

Learning is fitting a function

  • Define model, parameter, loss
  • Supervised vs unsupervised vs reinforcement
  • Train / validation / test split

Classical programming: you write the rules, the computer applies them to data. Machine learning flips it: you give examples of inputs with the correct outputs, and the computer finds the rules. "Finding the rules" means choosing numbers inside a function.

The four words everything rests on

  • Data: examples. Each example has features (inputs, written x) and often a label (the correct answer, written y).
  • Model: a function ŷ = f(x; θ) that turns an input into a prediction. The shape of the function is fixed by you.
  • Parameters θ: the adjustable numbers inside the model. Learning means picking good values for them.
  • Loss: one number that says how wrong the predictions are. Lower is better. Learning is the search for parameters that make the loss small.

The simplest model is a straight line: ŷ = w·x + b. Two parameters: the slope w (the weight) and the offset b (the bias). A common loss for predicting numbers is the mean squared error:

MSE = (1/N) · Σ (ŷᵢ − yᵢ)²

Squaring makes every error positive and punishes big errors much more than small ones.

Why you hide part of your data

A model can score perfectly on data it has seen by memorising it. What you care about is generalisation: performance on new data. So you split:

  • Training set (~70–80%): the model learns from it.
  • Validation set (~10–15%): you use it to make choices (which model, which settings).
  • Test set (~10–15%): touched once at the very end, to report an honest score.

Settings you choose yourself, not learned from data (like the shape of the model), are called hyperparameters. Parameters are learned; hyperparameters are chosen.

In the wild
  • Predicting energy use of a production line from temperature and load (regression).
  • Sorting welds into OK / defective from sensor readings (classification).
  • Grouping machines with similar vibration profiles without labels (clustering, unsupervised).

Phase A

Gradient descent: walking downhill

  • Derivative and gradient
  • Learning rate
  • Batch, mini-batch, stochastic

In Lab 1 you moved the sliders by feel. With millions of parameters that is impossible. We need an automatic rule that says which way to move each parameter.

The derivative is a slope

The derivative of the loss with respect to a parameter tells you: if I nudge this parameter up a tiny bit, does the loss go up or down, and how fast? With many parameters, the list of all these derivatives is the gradient, written ∇L. It points in the direction where the loss rises fastest.

So go the other way:

θ ← θ − η · ∇L(θ)

η (eta) is the learning rate: the step size. It is the single most important hyperparameter in practice.

  • Too small: training crawls.
  • Too large: you overshoot the valley, bounce around, or blow up to infinity (divergence).
  • Right: fast, steady descent.

How much data per step

  • Batch gradient descent: compute the gradient on the whole training set, then step. Accurate but slow.
  • Stochastic (SGD): one example per step. Noisy but cheap. The noise can even help escape small bumps.
  • Mini-batch: 32 to a few thousand examples per step. The standard choice because hardware processes a batch in parallel.

One full pass over the training set is an epoch.

Convex vs non-convex

The MSE of a straight line is a perfect bowl (convex): one bottom, and gradient descent always finds it. The models in the next unit give bumpy landscapes (non-convex) with many valleys. In practice, in very high dimensions most valleys turn out to be nearly as good as each other, which is why this simple rule works so well.

In the wild
  • Every neural network you have used, from photo filters to ChatGPT, was trained by some form of gradient descent.
  • Tuning the learning rate (and its schedule) is usually the first knob engineers turn when a training run misbehaves.

03
Phase A

Neurons, layers and backpropagation

  • Neuron = weighted sum + activation
  • Why non-linearity matters
  • Backprop = chain rule
  • Softmax & cross-entropy

A straight line can only draw straight boundaries. Real problems are curved. A neural network builds curved functions by stacking many simple units.

One neuron

z = w₁x₁ + w₂x₂ + … + b a = φ(z)

It is the line from Unit 1 with several inputs, followed by an activation function φ that bends the result.

Why the bend is essential: stacking linear functions gives another linear function. Ten layers without activation are mathematically one layer. The non-linearity is what lets depth add power.

Lab 3 · Activation zoopick a function

Layers

Put many neurons side by side and you get a layer. In matrix form: a = φ(W·x + b), where W is a matrix holding every weight of the layer. Feed one layer's output into the next and you get a multi-layer perceptron (MLP): input layer → hidden layers → output layer. "Deep" learning just means many hidden layers.

The universal approximation theorem says one wide enough hidden layer can approximate any reasonable function. Depth is used because it gets there with far fewer neurons: early layers build simple pieces, later layers combine them.

Backpropagation

Gradient descent needs the derivative of the loss for every weight. The network is a chain of functions, and the chain rule says the derivative of a chain is the product of the local derivatives:

∂L/∂w = ∂L/∂a · ∂a/∂z · ∂z/∂w

Backpropagation runs the network forward to get the loss (forward pass), then walks backward, layer by layer, multiplying local derivatives and reusing them (backward pass). It costs about twice the forward pass, no matter how many weights. Frameworks such as PyTorch do this for you (autograd), but you must be able to explain it.

Outputs for classification

For K classes the last layer outputs K raw scores called logits. Softmax turns them into probabilities that sum to 1:

softmax(zᵢ) = e^zᵢ / Σⱼ e^zⱼ

The matching loss is cross-entropy: L = −log(p_correct). If the model gives the correct class probability 0.9, loss is 0.105. If it gives 0.01, loss is 4.6. It punishes confident mistakes very hard. Remember softmax and cross-entropy: they come back in almost every later unit.

# PyTorch: a 2-layer MLP classifier, full training step
import torch, torch.nn as nn
model = nn.Sequential(nn.Linear(784, 128), nn.ReLU(), nn.Linear(128, 10))
opt = torch.optim.SGD(model.parameters(), lr=0.1)
logits = model(x)                          # forward pass
loss = nn.functional.cross_entropy(logits, y)  # softmax + -log p inside
opt.zero_grad(); loss.backward(); opt.step()  # backward pass + gradient step
In the wild
  • Tabular MLPs score credit risk and predict machine failure from sensor features.
  • Every classifier that outputs "92% cat" uses softmax on its final logits, and was trained with cross-entropy.

The bias–variance trade-off

Underfitting: the model is too simple, bad on training and validation. Overfitting: the model memorised the training set, including its noise; training loss is low but validation loss is high. The gap between the two curves is your overfitting alarm.

Fighting overfitting

  • More data or data augmentation (flips, crops, noise for images; paraphrases for text).
  • Weight decay (L2 regularisation): add λ·Σw² to the loss so large weights cost something. L1 (λ·Σ|w|) pushes weights to exactly zero.
  • Dropout: during training, randomly switch off a fraction (e.g. 10–50%) of neurons each step, so no neuron can rely on a specific partner. Turned off at inference time.
  • Early stopping: stop when validation loss stops improving.

Better optimisers

  • Momentum: keep a running average of past gradients, like a heavy ball that rolls through small bumps.
  • Adam: momentum plus a per-parameter step size scaled by how large that parameter's recent gradients were. The default for most deep learning. AdamW applies weight decay correctly and is the default for large language models later.
  • Learning-rate schedules: warm-up (start tiny, grow for the first steps) then decay (often cosine) toward zero.

Keeping gradients healthy

Backprop multiplies many local derivatives. If they are mostly below 1, the product shrinks to nothing in early layers (vanishing gradients). If mostly above 1, it explodes. Fixes you should be able to name:

  • ReLU-family activations (derivative is 1 on the positive side, unlike sigmoid's max of 0.25).
  • Careful initialisation (Xavier/Glorot, He) that keeps signal variance stable across layers.
  • Normalisation layers: rescale activations to mean 0, variance 1. BatchNorm normalises across the batch; LayerNorm normalises across the features of one example (does not depend on batch size).
  • Residual (skip) connections: output = x + F(x). The gradient has a direct highway back through the "+x" path. This is what made 100+ layer networks trainable (ResNet, 2015).
  • Gradient clipping: cap the gradient norm to stop explosions.
Debug ritual

Before a big run, try to overfit a single small batch. If the model cannot drive training loss near zero on 10 examples, there is a bug in the code, not a data problem.

In the wild
  • Dropout, weight decay and data augmentation are standard in almost every production vision model.
  • Residual connections are in every modern deep network: ResNets for vision and every transformer in the units ahead.

Tokenization: cutting text into pieces

  • Character vs word vs subword
  • Byte-Pair Encoding step by step
  • Vocabulary size trade-off

A token is the unit of text a model reads. The tokenizer maps text to a list of integer IDs from a fixed vocabulary, and back.

SchemeVocabularyProblem
Characterstiny (~100–300)sequences get very long; each piece carries little meaning
Whole wordshuge (millions)unknown words, typos, "run / runs / running" unrelated
Subwords30k–250kthe compromise used everywhere today

Byte-Pair Encoding (BPE)

  1. Start with every character (or byte) as its own token.
  2. Count every adjacent pair in the training text.
  3. Merge the most frequent pair into a new token and add it to the vocabulary.
  4. Repeat until you reach the target vocabulary size.

Frequent words end up as a single token; rare words split into known pieces. Working at the byte level means no input is ever "unknown". Variants: WordPiece (picks merges by likelihood), Unigram / SentencePiece (starts big and prunes; handles spaces as a normal symbol, useful for languages without spaces).

Consequences you will be asked about

  • Models see tokens, not letters. That is why they struggle to count letters in a word or reverse a string.
  • Cost and length limits are measured in tokens. English is roughly 0.75 words per token; French, Arabic and code often need more tokens for the same content, so they are more expensive.
  • Numbers get split oddly ("2026" might be "20" + "26"), which hurts arithmetic.
  • Special tokens mark structure: beginning/end of sequence, padding, and role markers in chat formats.
In the wild
  • Every LLM API bills per token and has a context limit in tokens.
  • Choosing or training a tokenizer is a real task when building a model for Arabic, French or code, where generic tokenizers waste tokens.

Phase B

Embeddings: meaning as geometry

  • One-hot vs dense vectors
  • Embedding table as a learned layer
  • Cosine similarity, word2vec, analogies
  • Sentence embeddings & semantic search

A token ID like 4012 is just a label; 4012 is not "close" to 4013. We need numbers where distance means something.

From one-hot to dense

A one-hot vector has as many slots as the vocabulary, all zero except a 1 at the token's ID. Every word is equally far from every other word. An embedding is a short dense vector (typically 256 to 8,192 numbers) learned so that tokens used in similar ways end up close together.

Mechanically, an embedding layer is a table with one row per token: shape vocab_size × d_model. Looking up row 4012 is the same as multiplying the one-hot vector by that matrix. The rows are parameters, trained with gradient descent like any weight.

Measuring closeness

cos(a, b) = (a · b) / (‖a‖ · ‖b‖) ∈ [−1, 1]

Cosine similarity compares direction only, ignoring length. 1 = same direction, 0 = unrelated, −1 = opposite. If vectors are normalised to length 1 first, cosine is just the dot product. Keep that in mind: the dot product is the star of Unit 8.

word2vec: learning embeddings from context

"You shall know a word by the company it keeps." word2vec (2013) trains a tiny network on a fake task: skip-gram predicts neighbouring words from a centre word; CBOW predicts the centre word from its neighbours. Nobody cares about the task; the learned embedding table is the prize. Negative sampling makes it cheap: instead of a softmax over the whole vocabulary, contrast the real neighbour with a few random words.

Directions in the space pick up meaning, which is why king − man + woman lands near queen. The same geometry also absorbs biases in the text (gender, ethnicity stereotypes), a known risk.

The limit: one vector per word

word2vec gives "bank" one vector whether it means river bank or money bank. Such embeddings are static. Units 8 and 9 show how to make them contextual: the vector for a token changes depending on the sentence around it.

Sentence embeddings and semantic search

You can also embed a whole sentence or paragraph into one vector (models such as Sentence-BERT, BGE, E5, or embedding APIs). Then:

  1. Embed every document once and store the vectors.
  2. Embed the user's query.
  3. Return the documents with the highest cosine similarity.

That is semantic search: it matches meaning, not exact keywords ("car" finds "automobile"). A database built to store vectors and find nearest neighbours fast is a vector database (FAISS library, Chroma, Qdrant, Milvus, pgvector). For millions of vectors they use approximate nearest neighbour indexes such as HNSW, trading a little accuracy for huge speed.

import numpy as np
# docs: (N, d) matrix of embeddings, q: (d,) query embedding
docs = docs / np.linalg.norm(docs, axis=1, keepdims=True)
q = q / np.linalg.norm(q)
scores = docs @ q                 # cosine = dot product after normalising
top_k = np.argsort(-scores)[:5]    # your own vector search, no library
In the wild
  • Semantic search in Notion, Google Drive or your own notes app (Mindscape) is embeddings + cosine similarity.
  • Recommendation systems ("customers who bought this…") embed products and users in one space.
  • Duplicate-ticket detection in support tools compares embeddings of new and old tickets.

Sequences before attention

  • Language modelling as next-token prediction
  • RNNs and hidden state

The task: predict what comes next

A language model assigns probabilities to sequences. The standard way: predict the next token given the ones before it, then multiply:

P(t₁ … tₙ) = P(t₁) · P(t₂ | t₁) · P(t₃ | t₁, t₂) · …

Training is supervised learning with free labels: in any text, every next token is the label for the text before it. The loss is the cross-entropy from Unit 3 over the vocabulary. Perplexity = e^(average cross-entropy): roughly "how many tokens is the model hesitating between". Lower is better.

The oldest version is the n-gram model: count how often each token follows the previous n−1 tokens. It cannot see further than n−1 tokens back and cannot generalise to unseen combinations.

Recurrent neural networks

An RNN reads one token at a time and keeps a hidden state vector h, a running summary of everything so far:

hₜ = tanh(W_h · hₜ₋₁ + W_x · xₜ + b)

The same weights are reused at every step. Training "unrolls" the loop through time and backpropagates through it (backpropagation through time).

Two fatal weaknesses

  1. Forgetting. Gradients pass through the same multiplication at every step, so over long sequences they vanish (Unit 4). The model forgets the start of long sentences. LSTM (1997) and GRU add gates, small learned valves (forget, input, output) that decide what to keep in a separate memory cell. This helps a lot, but does not fully fix it.
  2. No parallelism. Step t needs step t−1. You cannot process token 500 before token 499, so training on GPUs, which love parallel work, is slow.

The bottleneck in translation

Early sequence-to-sequence models (2014) used an encoder RNN to read the source sentence into one final hidden vector, and a decoder RNN to generate the translation from that single vector. A whole sentence squeezed into one fixed-size vector: long sentences fell apart.

The question that sets up Unit 8

What if, at each output step, the decoder could look back at every encoder state and choose which ones are relevant right now, instead of relying on one compressed summary?

Phase B

Attention: every token looks at every token

  • Query, Key, Value
  • Scaled dot-product attention
  • Why divide by √dₖ
  • Self-attention = contextual embeddings

Attention answers Unit 7's question. For each position, compute a weighted average of information from all positions, where the weights are learned from how relevant each position is.

The library analogy

Each token produces three vectors, each by multiplying its embedding by a learned matrix:

  • Query q = x·W_Q: "what am I looking for?"
  • Key k = x·W_K: "what do I contain, as a label?"
  • Value v = x·W_V: "what I will hand over if you pick me."

Relevance of token j to token i = dot product qᵢ · kⱼ (Unit 6: dot product measures alignment). Softmax turns relevance scores into weights summing to 1 (Unit 3). The output for token i is the weighted sum of all values.

Attention(Q, K, V) = softmax( Q·Kᵀ / √dₖ ) · V

With all tokens stacked into matrices, this is two matrix multiplications and a softmax: fully parallel, which fixes the RNN speed problem.

Why divide by √dₖ

dₖ is the length of the key vectors. If the entries of q and k are roughly random with variance 1, their dot product has variance dₖ. With dₖ = 128 the scores are in the tens, softmax becomes nearly one-hot, and its gradient is almost zero, so learning stalls. Dividing by √dₖ brings the variance back to 1. Play with it in the lab.

Self-attention vs cross-attention

  • Self-attention: Q, K and V all come from the same sequence. Every token updates itself using the others. This produces contextual embeddings: after one layer, "bank" in "river bank" and "bank account" already have different vectors. That solves the static-embedding limit of Unit 6.
  • Cross-attention: queries come from one sequence (the translation being written), keys and values from another (the source sentence). That is exactly the fix for the seq2seq bottleneck (Bahdanau attention, 2014).

The cost

Every token scores against every token: an n×n matrix. Compute and memory grow with n² in sequence length. Doubling the context quadruples attention cost. Remember this: it drives many engineering tricks in Unit 14.

def attention(Q, K, V, mask=None):   # Q,K,V: (n, d_k)
    scores = Q @ K.T / math.sqrt(K.shape[-1])   # (n, n) relevance
    if mask is not None:
        scores = scores.masked_fill(mask == 0, float("-inf"))
    weights = scores.softmax(dim=-1)             # each row sums to 1
    return weights @ V                           # weighted mix of values

  • The same attention operation runs inside every chatbot, code assistant and speech recogniser today.

The Transformer, block by block

  • Multi-head attention
  • Positional encoding
  • Causal mask

"Attention Is All You Need" (Vaswani et al., 2017) dropped recurrence entirely and built a network from attention plus pieces you already know from Units 3–4. This is the answer to "how does a transformer work?". Say it in this order.

1 · Positional encoding

Attention is a weighted sum; sums don't care about order. "dog bites man" and "man bites dog" would look identical. So we add position information to each token embedding:

  • Sinusoidal (original paper): fixed sine/cosine waves of different frequencies per dimension, so each position gets a unique pattern and relative offsets are easy to compute.
  • Learned absolute positions (GPT-2, BERT): one trainable vector per position.
  • RoPE (rotary, used by Llama, Mistral, Qwen): rotates q and k by an angle proportional to position, so their dot product depends on relative distance. Extends better to longer contexts.

2 · Multi-head attention

Instead of one attention with vectors of size d, run h heads in parallel, each with its own W_Q, W_K, W_V projecting to size d/h. Concatenate the results and mix them with an output matrix W_O. Same total cost as one big head.

Why: one softmax can only focus in one "way" at a time. Different heads learn different relations: one tracks the previous token, one links pronouns to nouns, one follows syntax. It is like several readers each looking for something different.

Lab 9 · Heads and the causal maskswitch heads, toggle mask

3 · The causal mask

For a model that generates text left to right, token i must not see tokens after it, or next-token prediction becomes cheating. Before softmax, set the scores above the diagonal to −∞; they become 0 after softmax. This lets the model train on every position of a sequence in one parallel pass while still only looking backward.

4 · The block

x = x + MultiHeadAttention(LayerNorm(x))   # tokens exchange information
x = x + FeedForward(LayerNorm(x))          # each token thinks alone
  • Feed-forward network (FFN / MLP): two linear layers with an activation (GELU or SwiGLU), applied to each token independently. Usually 4× wider inside. Holds about two-thirds of the parameters; much of the model's stored "knowledge" lives here.
  • Residual connections (Unit 4): each sub-layer adds to a residual stream instead of replacing it.
  • LayerNorm (Unit 4), usually placed before each sub-layer (pre-norm) for stable training. Many modern models use the cheaper RMSNorm.

Attention moves information between tokens; the FFN processes information within each token. Stack N identical blocks (12 for GPT-2 small, 80+ for large models).

5 · In and out

Tokens → embedding table (Unit 6) + positions → N blocks → final LayerNorm → a linear layer to vocabulary size (the LM head, often sharing weights with the embedding table) → softmax → probability of each next token.

Your 60-second interview answer

"Text is split into tokens, each mapped to a learned embedding plus position information. The sequence goes through a stack of identical blocks. In each block, multi-head self-attention lets every token build a weighted mix of the other tokens' values, with weights from softmax of scaled query-key dot products; a causal mask stops it seeing the future in a generator. Then a feed-forward network processes each token on its own. Residual connections and layer normalisation keep deep stacks trainable. A final linear layer and softmax give next-token probabilities, and it is trained with cross-entropy on huge text corpora. Because everything is matrix multiplication with no recurrence, it parallelises on GPUs, which is why it scaled."

  • Whisper (speech-to-text) and many translation systems are encoder-decoder transformers.

Pre-training and decoding

  • Pre-training at scale
  • Scaling laws
  • Temperature, top-k, top-p

A large language model (LLM) is a decoder-only transformer (Unit 9) with billions of parameters, trained on next-token prediction (Unit 7) over trillions of tokens of text and code.

Pre-training

  • Data: web crawls (Common Crawl), books, code, papers, cleaned by deduplication, quality and toxicity filters, language ID. Data quality matters as much as size.
  • Compute: thousands of GPUs for weeks. A rule of thumb: training compute ≈ 6 × parameters × tokens (FLOPs).
  • Result: a base model (or foundation model). It continues text; it does not follow instructions yet. Ask it a question and it may answer with more questions.

Scaling laws

Kaplan et al. (2020) showed loss falls smoothly and predictably as a power law in parameters, data and compute. Chinchilla (Hoffmann et al., 2022) found the compute-optimal ratio is about 20 training tokens per parameter; earlier models were too big for their data. Modern small models are deliberately "over-trained" far past that ratio because they are cheaper to run afterwards.

Some abilities (multi-step arithmetic, following examples in the prompt) appear only at larger scale: emergent abilities. In-context learning: the model picks up a task from examples in the prompt without any weight change (few-shot; with no examples, zero-shot).

Decoding: turning probabilities into text

At each step the model outputs a probability for every token. You pick one, append it, and run again: autoregressive generation.

  • Greedy: always take the most likely. Deterministic, often repetitive.
  • Beam search: keep the k best partial sequences. Good for translation, bland for chat.
  • Temperature T: divide logits by T before softmax. T<1 sharpens (safer), T>1 flattens (more creative, more errors). T→0 equals greedy.
  • Top-k: sample only among the k most likely tokens.
  • Top-p (nucleus): sample among the smallest set whose probabilities add up to p (e.g. 0.9). Adapts to how confident the model is.

Post-training and fine-tuning

  • SFT / instruction tuning
  • RLHF, reward models, DPO
  • Full fine-tuning vs PEFT

Turning a base model into an assistant happens in stages, usually called post-training or alignment.

Stage 1 · Supervised fine-tuning (SFT)

Continue training on tens of thousands of high-quality (instruction, ideal answer) pairs, written by people or by stronger models. Same next-token loss, but usually computed only on the answer tokens. Conversations are wrapped in a chat template with special role tokens (system, user, assistant). Result: an instruct or chat model.

Stage 2 · Preference tuning

It is easier for people to say which of two answers is better than to write the perfect one.

  • RLHF (reinforcement learning from human feedback, the InstructGPT recipe): collect pairs ranked by humans → train a reward model that scores answers → optimise the LLM with reinforcement learning (Unit 1: maximise reward), typically PPO, with a penalty (KL divergence) for drifting too far from the SFT model so it does not "hack" the reward.
  • DPO (direct preference optimisation, 2023): skips the separate reward model and RL loop; a simple classification-style loss directly raises the probability of preferred answers over rejected ones. Simpler and stable; very common in open models.
  • RLAIF / Constitutional AI: an AI model, guided by written principles, provides the preference labels.
  • RL with verifiable rewards: for maths and code, the reward is simply "is the answer correct / do the tests pass". This is how reasoning models (OpenAI o-series, DeepSeek-R1 with GRPO) learn to write long chains of thought before answering.

Should you fine-tune?

Order of attempts in industry: good prompting → retrieval (Unit 12) → fine-tuning. Fine-tune to change behaviour, format or style, or to specialise a small model to replace a big one. Don't fine-tune just to add facts that change; retrieval handles that better.

Parameter-efficient fine-tuning (PEFT)

Full fine-tuning of a 7B model needs memory for weights, gradients and Adam's two extra values per parameter: over 100 GB. PEFT freezes the original weights and trains a small add-on.

LoRA (low-rank adaptation): for a frozen weight matrix W of shape d×k, learn the change as the product of two thin matrices:

W' = W + (α/r) · B·A B: d×r, A: r×k, r ≪ d

B starts at zero, so training starts exactly from the original model. Typically applied to the attention projections (W_Q, W_V…). After training you can merge B·A into W: no extra inference cost. Adapters are a few MB, so you can keep one per task and swap them.

QLoRA: keep the frozen base in 4-bit precision (see Unit 14) and train LoRA adapters on top. Fine-tuning a 7B model fits on a single consumer GPU. Tools: Hugging Face transformers + peft + trl, Unsloth, Axolotl.

Prompting and RAG

Two limits of any LLM

  • Context window: the maximum tokens it can read at once (prompt + answer). From 4k to over 1M today. Remember n² from Unit 8: long contexts are costly, and models attend less reliably to the middle ("lost in the middle").
  • Hallucination: the model is trained to produce plausible next tokens, not true ones. When it lacks the fact, it produces something that looks right. Its knowledge also stops at a training cutoff, and it has never seen your private data.

Prompt engineering that actually matters

  • System prompt: role, rules, output format, set once.
  • Be specific; give the model the context a new colleague would need.
  • Few-shot examples (Unit 10) for format and edge cases.
  • Chain-of-thought: ask it to reason step by step before answering; improves maths and logic.
  • Structured output: ask for JSON matching a schema; many APIs can enforce it.
  • Delimit inputs (XML tags, triple quotes) so data is not mistaken for instructions, which is also a first defence against prompt injection.

Retrieval-augmented generation

RAG (Lewis et al., 2020) means: before answering, search your documents and paste the relevant pieces into the prompt. The model answers from the evidence instead of from memory. It combines semantic search (Unit 6) with generation. Benefits: fresh data without retraining, private data, fewer hallucinations, and citations to the source.

Lab 12 · A RAG pipeline, liveask about the plant

The two halves

Indexing (offline): load documents → split into chunks (e.g. 300–1,000 tokens with 10–20% overlap, ideally along headings or paragraphs) → embed each chunk → store vectors + text + metadata (source, page, date) in a vector database.

Query (online): embed the question → retrieve top-k chunks → optionally rerank → build the prompt ("Answer only from the context; say you don't know otherwise; cite sources") → generate.

What makes RAG good rather than a demo

  • Hybrid search: combine vector search with keyword search (BM25). Vectors catch meaning; keywords catch exact part numbers, error codes and names.
  • Reranking: retrieve 20–50 candidates fast, then re-score them with a cross-encoder (a model that reads the query and chunk together, like BERT from Unit 9). Slower but much more precise. Keep the best 3–5.
  • Query rewriting: turn a vague follow-up ("and the other one?") into a standalone question; or generate a hypothetical answer and search with it (HyDE).
  • Metadata filters: restrict by machine, date, access rights.
  • Variants you may hear: GraphRAG (retrieve over a knowledge graph), agentic RAG (the model decides when and what to search; Unit 13).

RAG failure has two places to look: retrieval (the right chunk was never found) or generation (it was found but ignored or misread). Measure them separately; Unit 16 shows how.

In the wild
  • Customer-support bots answering from help-center articles.
  • Internal "chat with our docs" tools over manuals, contracts, maintenance logs.
  • Your Mindscape whisper: retrieve related notes, then let the model suggest links.

Tool calling

You describe functions to the model (name, description, JSON schema of arguments). Instead of plain text, the model can reply "call get_machine_status with {"line": 3}". Your code executes it and sends the result back; the model continues. The model never runs anything itself: it only writes structured requests. This is function calling, and it is how LLMs reach calculators, databases, APIs and robots.

What makes it an agent

An agent is an LLM in a loop that decides its own next step until the goal is reached. The classic pattern is ReAct (Reason + Act, 2022): Thought → Action (tool call) → Observation (result) → Thought → … → Final answer. Add memory (short-term: the conversation; long-term: facts saved to a store and retrieved later) and planning (break the goal into steps first).

Vision, diffusion, multimodal

  • CNNs
  • Vision Transformer patches

Convolutional neural networks

A CNN slides small learned filters (e.g. 3×3) across an image. Early filters detect edges, later ones textures, parts, objects. Weight sharing (same filter everywhere) makes them efficient, and pooling shrinks the image step by step. ResNet (Unit 4's skip connections) dominated vision for years. Still the default on small edge devices and industrial inspection.

Vision Transformer (ViT)

Cut the image into fixed patches (e.g. 16×16 pixels), flatten each into a vector, and treat patches exactly like tokens: embeddings + positions → transformer blocks. With enough data it matches or beats CNNs, and it lets one architecture handle text and images.

Lab 14 · Patches and noiseViT patching · diffusion forward process

CLIP: one space for images and text

Train an image encoder and a text encoder together on 400M (image, caption) pairs. Contrastive loss: in each batch, pull the embedding of each image toward its own caption and push it away from all other captions. Result: images and text share one embedding space (Unit 6), enabling zero-shot classification ("a photo of a cracked weld" vs "a photo of a good weld") and image search by text.

Multimodal LLMs

Attach a vision encoder (often CLIP-like) to an LLM through a small projection layer that turns image features into "visual tokens" the LLM reads alongside text (LLaVA pattern; GPT-4o, Claude, Gemini, Pixtral, Qwen-VL). Audio works the same way (Whisper encodes speech).

Diffusion models

Forward process: add a little Gaussian noise over many steps until the image is pure noise (the lab slider). Reverse process: train a network to predict the noise that was added at step t; subtract it step by step, starting from random noise, to generate a new image. Conditioning on a text embedding (via cross-attention, Unit 8) steers what appears. Latent diffusion (Stable Diffusion) runs this in a compressed space for speed; newer models use transformers as the denoiser (DiT). Earlier generative approaches: GANs (generator vs discriminator game) and VAEs.

  • Visual inspection on production lines (CNNs on edge cameras).
  • Searching a photo library by typing "red car at night" (CLIP-style embeddings).
  • Image generation tools (diffusion) and assistants that read screenshots (multimodal LLMs).

Two phases

  • Prefill: process the whole prompt in parallel. Compute-heavy. Sets the time to first token (TTFT).
  • Decode: generate one token at a time (Unit 10). Sets tokens per second.

KV cache

At each decode step, the new token needs the keys and values of all previous tokens (Unit 8). Recomputing them every step is wasteful, so they are stored: the KV cache. It grows with context length × layers × heads and can take more memory than the weights for long contexts. Tricks: grouped-query attention (GQA: several query heads share one K/V head), PagedAttention (vLLM manages the cache like OS memory pages), sliding-window attention (Mistral 7B).

The memory wall

During decode, every weight must be read from memory once per token, but each weight is used for only about two operations. The GPU spends most of its time waiting for data. Decode is memory-bandwidth bound:

max tokens/s ≈ memory bandwidth (GB/s) ÷ model size in memory (GB)

A 7B model in 16-bit is 14 GB; on a 1,000 GB/s GPU that caps at about 70 tokens/s per request. Batching many users reuses each weight read for many tokens, which is why servers use continuous batching.

Quantization

Store weights with fewer bits: FP32 → FP16/BF16 → INT8 → INT4. Half the bits means half the memory and roughly double decode speed, with small quality loss down to about 4 bits.

  • Post-training quantization methods: GPTQ, AWQ (protects the most important weights), GGUF formats (Q4_K_M etc., used by llama.cpp and Ollama).
  • Quantization-aware training: simulate low precision during training for better results.
  • Pitfall: outlier values in activations; methods like SmoothQuant move them into the weights.

Other speed-ups

  • FlashAttention: computes attention in tiles inside fast on-chip memory, never writing the n×n matrix to slow memory. Same result, much faster.
  • Speculative decoding: a small draft model guesses several tokens; the big model checks them all in one pass.
  • Distillation: train a small student to imitate a large teacher's outputs.
  • Pruning: remove unimportant weights or whole heads.
  • Mixture of Experts (MoE, e.g. Mixtral, DeepSeek): many FFN "experts" per layer but a router activates only 2 per token. Huge total parameters, small compute per token (still large memory).

Serving stack

Local: Ollama, llama.cpp, LM Studio. Servers: vLLM, TGI, TensorRT-LLM, SGLang. Portable: ONNX Runtime. Browser: WebLLM (WebGPU), Transformers.js. Phones and NPUs: ExecuTorch, Core ML, and on Huawei hardware MindSpore with the Ascend NPU (CANN toolkit) and MindSpore Lite for devices.

Edge AI runs the model on the device: privacy (data never leaves), no network latency, works offline, no per-call cost; limited by memory, bandwidth and power, which is why quantization and small models matter so much there.

In the wild
  • Running Mistral or Llama on a laptop with Ollama uses 4-bit GGUF quantization.
  • On-device assistants in phones (and Huawei's NPUs) depend on quantization and small models.
  • vLLM's PagedAttention and continuous batching are why hosted APIs can serve thousands of users per GPU.

Classic metrics

Accuracy lies when classes are imbalanced: if 1% of parts are defective, "always say OK" is 99% accurate and useless. Use the confusion matrix:

  • Precision = TP / (TP + FP): of what I flagged, how much was right.
  • Recall = TP / (TP + FN): of what was really there, how much I caught.
  • F1 = harmonic mean of the two. ROC-AUC: quality across all thresholds.

Moving the decision threshold trades one against the other. For defect detection or fraud, missing one is costly: favour recall. For spam, a false alarm is costly: favour precision.

Evaluating LLMs

  • Benchmarks: MMLU (knowledge), GSM8K / MATH (maths), HumanEval / SWE-bench (code), GPQA (hard science), MT-Bench and Chatbot Arena (human preference). Beware contamination: test questions leaked into training data.
  • LLM-as-a-judge: a strong model grades outputs against a rubric. Cheap and scalable, but has biases (prefers longer answers, its own style, the first option).
  • For your own product, build a golden dataset: 50–200 real questions with expected answers, run it on every change (regression testing).

MLOps: keeping models alive

  • Experiment tracking: MLflow, Weights & Biases (every run's settings, metrics, artifacts).
  • Versioning of data, code and models (DVC, model registry). Reproducibility: fixed seeds, pinned versions.
  • Deployment: containers (Docker), APIs (FastAPI), Kubernetes; CI/CD with evaluation gates.
  • Monitoring: latency, cost per request, error rates, and drift: the real-world data slowly stops looking like training data (new product line, new sensor), so performance silently decays. For LLM apps: tracing each call (LangSmith, Langfuse).

Responsible AI

  • Bias and fairness: models reproduce patterns in data (Unit 6's embedding biases). Measure performance per group.
  • Privacy: GDPR; personal data in training sets and prompts; models can memorise and leak. On-device inference (Unit 15) and anonymisation help.
  • Security: prompt injection (instructions hidden in retrieved documents or web pages), jailbreaks, data exfiltration through tools, excessive agent permissions. See the OWASP Top 10 for LLM applications.
  • Explainability: SHAP, LIME for classic models; attention maps and interpretability research for transformers.
  • EU AI Act (in force since 2024, obligations phased in 2025–2027): risk tiers (unacceptable, high, limited, minimal); high-risk systems (e.g. safety components, hiring) need risk management, data governance, documentation, human oversight; general-purpose models have transparency duties.
In the wild
  • Quality gates in CI that block a new prompt or model if the golden-set score drops.
  • Drift dashboards that alert when a sensor's data no longer looks like training data.
  • Compliance files (risk assessment, data sheets) prepared for high-risk systems under the EU AI Act.
